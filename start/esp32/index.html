    ESP32 Devices¶

    Newmota on Espressif ESP32 chips (ESP32, C2/C3/C5/C6/C61, S2/S3/S31, P4/P4X, H2) using upstream ESP-IDF v5.5 or v6.1. This is the leading platform: if a feature exists anywhere, it exists here first. All ESP32 builds carry the device-hosted web interface, LittleFS file browser, Berry console, MQTT, and Safeboot recovery.

    Supported Microcontrollers¶

    • ESP32 (Classic dual-core Wi-Fi + BLE)
    • ESP32-C2 (Ultra-low-cost RISC-V 2 MiB Wi-Fi + BLE)
    • ESP32-C3 (Mainstream RISC-V 4 MiB Wi-Fi + BLE)
    • ESP32-C5 / ESP32-C6 / ESP32-C61 (Dual-band 2.4/5GHz Wi-Fi 6 + Thread/Zigbee/BLE)
    • ESP32-S2 / ESP32-S3 / ESP32-S31 (High-performance Xtensa LX7 with USB-OTG / CDC & OPI/QSPI PSRAM; S31 defaults to IDF 6.1 and is an SDK preview whose bootloader accepts images with an invalid SHA-256 hash: bring-up only)
    • ESP32-P4 / ESP32-P4X (High-performance RISC-V application SoC; P4X is revision 3.x silicon, maps to SDK target esp32p4, and defaults to IDF 6.1)
    • ESP32-H2 (IEEE 802.15.4 + BLE 5 leaf node)

    Build & Flashing Pipeline¶

    ESP-IDF targets use idf.py and CMake directly through Newmota's Python platform adapter (tools/newmota/platforms/esp/build.py).

    Native Packaging & Safeboot Pairing¶

    A successful ESP-IDF build writes an immutable development factory package under build/firmware/<environment>/<version>/:

    build/firmware/esp32c2-2m/<version>/
├── manifest.json       # Immutable package manifest with SHA-256 checksums
├── bootloader.bin      # ESP-IDF compiled bootloader
├── partition-table.bin # Compiled partition table
├── factory.bin         # Combined factory flash image
└── filesystem.bin      # Pre-generated LittleFS partition image

    Environments declare explicit roles (application vs safeboot under config/env/esp-idf/<role>/). When building an application with a declared safeboot dependency (e.g. esp32s3-qio-qspi referencing esp32s3-qio-qspi-safeboot), the build pipeline automatically compiles and verifies the safeboot image before producing the final application package.

    At runtime, Newmota supports Tasmota-compatible partition switching via the Restart 3 command. When triggered on an ESP-IDF target with a single-OTA Tasmota partition table, it updates the otadata boot sector to toggle between app0 and safeboot without manual reflashing.

    Dynamic Partition Auto-Scaling¶

    When flashing an ESP32 target with make flash ENV=<env>, Newmota probes the physical flash chip size via esptool. If the physical chip capacity exceeds the package layout (for example, a 4 MiB device running a 2 MiB package), Newmota automatically regenerates a temporary partition table:

    1. Keeps fixed bootloader, app, and system offsets unchanged.
    2. Expands only the trailing LittleFS filesystem partition to utilize remaining physical space.
    3. Writes the resized partition table and extended filesystem image safely.

    A device smaller than the package is rejected. Probe data and the exact write plan are kept under build/work/<environment>/flash/<size>/. Flash-only setup installs ESP-IDF's pinned Python programming and monitoring environment without a compiler.

    Serial Console & USB Hardware Workflow¶

    ESP-IDF builds use a single application console for both system logs and interactive commands (src/platform/esp-idf/console.cpp).

    Dynamic USB vs. UART0 Console Detection¶

    For boards configured with on-chip USB (usb-cdc or usb-serial-jtag, such as ESP32-S3):

    • During boot, Newmota actively monitors the USB hardware Start-of-Frame (SOF) counter for up to 250 ms.
    • If an active USB host connection is detected, the firmware activates the USB console.
    • If no host activity occurs within 250 ms, it cleanly falls back to UART0 for the lifetime of the boot session.
    • A board recipe with console: uart0 skips the USB probe entirely.

    Control-Line-Safe USB Monitor¶

    Standard ESP-IDF monitor toggles DTR and RTS lines upon opening serial ports. On the ESP32-S3's built-in USB Serial/JTAG port (303a:1001), this assertion sequence forces the chip back into the ROM bootloader instead of attaching to the running application.

    Newmota implements a custom control-line-safe launcher (tools/newmota/platforms/esp/usb_monitor.py):

    • No DTR/RTS Assertion: Attaches to the serial stream without modifying flow control lines.
    • Watchdog Reset: Flashing operations on USB Serial/JTAG finish with an explicit esptool watchdog_reset, cleanly booting the newly written SPI application before the monitor attaches.
    • USB Re-enumeration: The -monitor targets wait for the USB device to re-enumerate post-flash before attaching.
    • External UART adapters continue using standard hardware reset behavior.

    The built-in USB Serial/JTAG controller (303a:1001) is not the same as native USB-OTG CDC (303a:0009). The S3 recipes follow Tasmota and use USB Serial/JTAG; their ser variants use UART0. USB-OTG CDC is not a generic S3 default, because with the internal PHY it needs the USB_PHY_SEL eFuse or hardware with a separately wired external PHY. MONITOR_PORT and MONITOR_BAUD also apply after re-enumeration.

    Web & Telemetry Services¶

    Normal Wi-Fi ESP-IDF application builds include the device-hosted web service (UI, LittleFS file browser, and dual Web/Berry consoles) via the native ESP-IDF HTTP/HTTPS server, as well as bounded plain MQTT client and telemetry services. Every ESP-IDF application has an exact-board Safeboot environment, including the 2 MiB ESP32-C2 target (esp32c2-2m + esp32c2-2m-safeboot).

    Capacity & Feature Allocation¶

    • 2 MiB Targets (e.g. esp32c2-2m): Both application and Safeboot fit their partition budgets; served via HTTP+Gzip on port 80; WPA3-SAE is omitted to conserve flash.
    • 4 MiB+ Targets (e.g. esp32c3-4m, esp32s3-qio-opi): Served via HTTP+Gzip on port 80 (Standard profile); Large profiles (ESP32-P4, ESP32-S31, esp32s3-qio-opi-8m-8m) default to HTTPS on port 443 with Brotli-compressed assets and a self-signed certificate. Either default can be flipped with USE_WEB_HTTPS. Both retain full WPA3-SAE, BearSSL crypto module, and large LittleFS filesystems.
    • WPA3 on BearSSL: On both ESP-IDF tracks, chips with their own Wi-Fi radio run the Wi-Fi supplicant on BearSSL with their SHA-1, SHA-256 and P-256 hardware instead of the SDK's mbedTLS (USE_WIFI_WPA3_BEARSSL, on by default in application and Safeboot). Images without HTTPS then link no mbedTLS and are smaller (esp32c3: 1,137,792 B instead of 1,214,208 B). On ESP32-S31 (6.1 track) the Safeboot image shrinks from 958,304 B to 837,296 B. It needs the Newmota ESP-IDF fork, which the build checks out for both tracks. ESP32-P4 and ESP32-P4X reach Wi-Fi through ESP-Hosted, where the companion chip runs the supplicant, so they keep their previous setup, as does ESP32-H2. Set USE_WIFI_WPA3_BEARSSL: false in a personal build for the mbedTLS supplicant.
    • Dual ESP-IDF Tracks: Targets default to the pinned ESP-IDF 5.5 track. Environments or personal configs can select the 6.1 track via idf_version: "6.1" (default on ESP32-S31).
    • Matter & BLE: Both are implemented but no checked-in profile selects them. USE_MATTER needs at least 4 MiB flash and hardware entropy and runs only on ESP-IDF here; USE_MATTER_BLE additionally selects USE_BLE. Add them in a personal build, then enable Matter with SetOption151 1 and restart. See Matter and Bluetooth & BLE Sensors.
    • Settings Migration: The Tasmota 15.5.0.2 settings importer supports all eight ESP targets (ESP32, S2, S3, C2, C3, C5, C6, and P4), copying preserved Wi-Fi slots, preferred slot, and compatible web passwords on first boot.
