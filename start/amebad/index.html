    AmebaD BW16 Devices¶

    Newmota on Realtek dual-core Wi-Fi + BLE microcontrollers (RTL8720D/DN, BW16 modules).

    Supported Microcontrollers¶

    • RTL8720DN / BW16 (Dual-core ARM Cortex-M0 + Cortex-M4 Wi-Fi/BLE module, 2 MiB Compact)

    Dual-Core Build Lifecycle¶

    The AmebaD platform adapter (tools/newmota/platforms/amebad/build.py) orchestrates vendor Makefile compilation for both onboard CPU cores:

    1. KM0 Core (Cortex-M0): Low-power engine and boot controller.
    2. KM4 Core (Cortex-M4): High-performance application core running Newmota's C++ core (src/app/core/) and RTOS services.
    # Build the baseline BW16 2 MiB environment (plus its safeboot companion)
make bw16-2m

    The bw16-2m application environment declares safeboot: bw16-2m-safeboot; the pipeline builds the safeboot image first, then the application.

    Serial Makefile Execution¶

    Because AmebaD SDK Makefiles share clean and build targets that race under parallel make, the platform adapter executes native AmebaD builds serially while retaining parallel job execution for single-core targets.

    Output Artifacts¶

    A successful build generates the vendor KM0, KM4, combined image, AXF, and map under build/work/bw16-2m/. The packager (tools/newmota/platforms/amebad/images.py, device driver device.py, host uploader uploader.py) writes a paired factory package under build/firmware/bw16-2m/<version>/ containing the Safeboot and application image2 outputs, both boot images, an empty 64 KiB LittleFS image, the pinned flashloader, and the community Python write/verify uploader plan with manifest + SHA-256 hashes.

    2 MiB Factory Layout¶

    The factory layout follows the ESP 2 MiB split, with boot images retained at 0x0000 and 0x4000:

    Region Offset Size Content
    Boot images 0x0000, 0x4000 — Vendor boot images (retained)
    Safeboot / OTA1 0x010000 0x0C8000 Safeboot image2
    Application / OTA2 0x0D8000 0x118000 Application image2
    LittleFS 0x1F0000 0x10000 (64 KiB) Filesystem (native adapter)

    The factory path verifies the flashloader's word-sum checksums. The package manifest records hashes before any device is opened.

    Wired Operations¶

    # Factory flash. Enter UART download mode when prompted,
# then reset the board manually after verification.
# Use an explicit port while this path is experimental.
make flash ENV=bw16-2m PORT=/dev/cu.usbserial-0001

# Update: writes only the coupled KM0/KM4 application image into OTA2.
# Enter UART download mode when prompted, then reset manually.
# A device currently in Safeboot remains there (boot selection is preserved).
make update ENV=bw16-2m PORT=/dev/cu.usbserial-0001

    Upload runs at 230400 baud and the console at 115200 (override with BAUD/MONITOR_BAUD). probe and backup are not available.

    make update runs the SDK's coupled KM0/KM4 build and writes only the combined application image to OTA2. It does not build Safeboot or a filesystem package and is not the signed remote OTA implementation.

    Web & Network Services¶

    AmebaD is the second native web port after ESP32-C2: Wi-Fi application builds serve the shared HTTP+Gzip UI through Realtek's native HTTPD library (src/platform/amebad/web.cpp) behind the same bounded web.h application interface. The 2 MiB Compact image serves HTTP; HTTPS is an opt-in build feature (USE_WEB_HTTPS), and browser-behavior hardware testing remains pending. See Web Interface.

    SoftAP onboarding (192.168.4.1): the latest BW16 log confirms station and AP operation, the 192.168.4.1 address, DHCP, and scan results. Browser onboarding routes and AP restart mode need a hardware retest, and scan warnings during multi-channel concurrency and client stability remain open. MQTT operates over the shared TCP transport layer (src/platform/lwip/tcp_stream.cpp), the same as on ESP32. See MQTT & Telemetry for configuration.

    Hardware testing¶

    Seen on BW16 hardware: factory write/verify, manual reset, clean LittleFS 2.0 initialization, settings persistence, Wi-Fi/NTP startup, setup AP with DHCP and scanning, serial monitoring, and Restart 3 image switching. The OTA1/OTA2 layout above is newer than the earlier trials, so browser onboarding and the current update layout still need testing.

    Still open: make probe and make backup (unavailable), OTA2-only update testing, recovery, automated reset, and broader testing. See Build System Internals and Console & Commands (Restart 3) for what each operation writes.
