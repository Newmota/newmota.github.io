    Raspberry Pi Pico W & Pico 2 W¶

    Newmota on the Raspberry Pi Pico 2 W (RP2350, 4 MiB flash) and original Raspberry Pi Pico W (RP2040, 2 MiB flash) using the official Pico SDK v2.3.1. For flashing you put the board in BOOTSEL mode; day-to-day use is identical to every other device — browser and console.

    Hardware Specifications¶

    Specification Raspberry Pi Pico 2 W Raspberry Pi Pico W
    Microcontroller Raspberry Pi RP2350 (Dual Arm Cortex-M33 @ 150 MHz, FPU / DSP) Raspberry Pi RP2040 (Dual Arm Cortex-M0+ @ 133 MHz)
    Wireless Subsystem Infineon CYW43439 (2.4 GHz Wi-Fi 4 + BLE 5.2) Infineon CYW43439 (2.4 GHz Wi-Fi 4 + BLE 5.2)
    Physical Flash 4 MiB QSPI Flash 2 MiB QSPI Flash
    Profile Standard Profile (4 MiB baseline, HTTP+Gzip default) Compact Profile (2 MiB baseline, HTTP+Gzip default)
    Console USB CDC serial console (stdio_usb) USB CDC serial console (stdio_usb)
    Environments pico2-w (+ pico2-w-safeboot) pico-w (+ pico-w-safeboot)

    Native Build & Toolchain Integration¶

    The Raspberry Pi build adapter (tools/newmota/platforms/pico/build.py) coordinates native CMake builds against upstream Pico SDK:

    Managed Toolchain & Programmer¶

    • Cross-Compiler: Pinned Arm GNU bare-metal toolchain (xpack-arm-none-eabi-gcc v14.2.1-1.1), managed under ~/.newmota/tools/arm-none-eabi/ and shared with the Beken target.
    • Programmer Utility: Pinned official picotool v2.3.1, managed under ~/.newmota/tools/pico-sdk/picotool-2.3.1/.
    • SDK Version Declaration: config/sdk/pico-sdk.toml pinning commit 079c6f39023649b154152db30f1d781e884879bc.

    Native Lifecycle Stages¶

    1. Configure: Invokes CMake (Unix Makefiles) pointing to src/platform/pico-sdk/native/CMakeLists.txt with target platform (rp2350 or rp2040) and board (pico2_w or pico_w).
    2. Build: Compiles application core C++ sources and Pico SDK native drivers into build/work/<env>/native/.
    3. Compilation Database: Generates compile_commands.json for IDE integration via make clangd ENV=pico2-w or make clangd ENV=pico-w.
    4. Post-Build Artifacts: Produces binary output files:
    5. newmota.elf: Debug binary with complete symbol tables.
    6. newmota.bin: Raw flashable binary image.
    7. newmota.uf2: Drag-and-drop USB bootloader binary.

    Building Pico Firmware¶

    # Explicit toolchain and SDK setup
make setup PLATFORM=pico

# Build Pico 2 W (RP2350, 4 MiB)
make pico2-w

# Build original Pico W (RP2040, 2 MiB)
make pico-w

    The pico2-w target is also included in the routine cross-platform test matrix executed by make test.

    Application environments declare their companion safeboot dependencies (safeboot: pico2-w-safeboot or safeboot: pico-w-safeboot); the pipeline builds the safeboot image first, then the application. Each role links at its own slot base with linker-enforced budgets.

    Partition Layouts¶

    RP2350 4 MiB Layout (4m-rp2350.json)¶

    The RP2350 uses picotool JSON partition definitions on the RP2350 boot ROM image-chain API. Safeboot starts at flash offset zero and embeds the resident partition table; the table-free application sits behind it and is linked at XIP_BASE, because the ROM rolls the chosen flash partition into the runtime window when it chains. The resolver pins this geometry exactly, so an unreviewed edit fails closed.

    Region Offset Size Content
    Safeboot 0x000000 0x0D0000 Recovery image; owns the embedded native partition table
    Application 0x0D0000 0x2D2000 Normal firmware (table-free launchable image)
    Data 0x3A2000 0x05B000 Marker sector + LittleFS
    ├─ Sticky-boot marker (platform-owned) 0x3A2000 4 KiB Power-cycle-persistent Safeboot request, outside the LittleFS geometry
    └─ LittleFS 0x3A3000 0x05A000 Filesystem (native adapter in src/platform/pico-sdk/filesystem.cpp)
    BTstack reserve 0x3FD000 0x002000 Reserved
    E10 last-sector reserve 0x3FF000 4 KiB Preserved

    Both images use secure-only executable permissions with independent (unlinked) slots; the TBYB IMAGE_DEF bit stays clear on both so factory and normal boots just work. A rendered standalone table ships in the package as a reference only and is not flashed.

    RP2040 2 MiB Layout (2m-rp2040.json)¶

    Region Offset Size Content
    Safeboot 0x000000 0x0C0000 Recovery image
    Application 0x0C0000 0x12F000 Normal firmware
    Boot marker 0x1EF000 4 KiB Sticky-boot marker
    LittleFS 0x1F0000 0x010000 (64 KiB) Filesystem (cached reads, normal writes enabled)

    Boot selection and updates¶

    Restart 3 arms the marker and the entry point chains into Safeboot before any service starts; a failed chain clears the request so a corrupt Safeboot image cannot reboot-loop. The wired update rebuilds the single application image and writes only the application slot after validating the installed Newmota table; Safeboot, LittleFS, the marker, and the reserves are untouched (the marker is preserved, so a device in Safeboot stays there).

    Storage & Filesystem Status¶

    • Serial Console: Operates over native USB CDC (pico_stdio_usb); uses the common serial monitor.
    • Filesystem Adapter: Native LittleFS block-device adapter (src/platform/pico-sdk/filesystem.cpp) over the dedicated update-preserved region behind the marker sector. Settings are kept there and not duplicated into vendor stores.
    • Boot selection: Platform-owned marker sector (src/platform/pico-sdk/boot_select.h), outside the LittleFS geometry.

    Wired Operations¶

    make probe ENV=pico2-w PORT=/dev/cu.usbserial-0001
make backup ENV=pico2-w PORT=/dev/cu.usbserial-0001 OUTPUT=pico2w-stock.bin
make flash ENV=pico2-w PORT=/dev/cu.usbserial-0001
make update ENV=pico2-w PORT=/dev/cu.usbserial-0001

    The factory package carries both FW images and an empty LittleFS image. Factory provisioning performs identity/capacity preflight and can replace a virgin or foreign table; application-only updates additionally require the exact installed Newmota table and verify each component by read-back. picotool operations need the board in BOOTSEL mode; a running Newmota image usually reboots into BOOTSEL by itself, otherwise hold BOOTSEL while connecting or resetting the board. UF2 files remain native build artifacts rather than package components.

    Note

    picotool file-model operations on large binaries (info, uf2 convert) were observed throwing std::bad_alloc on the macOS host build. Build-time partition embedding (ELF path) and all host-side byte-level checks are unaffected; device-path operations are hardware testing scope.

    Optional Wireless Features¶

    The CYW43439 provides BLE 5.2, and the firmware can use it, but no checked-in Pico profile selects BLE or Matter:

    • USE_BLE / USE_BLE_SENSORS compile the Pico SDK BTstack backend and native sensor decoding. Pico W/RP2040 needs a separate variant; the adapter is compile-tested only. See Bluetooth & BLE Sensors.
    • USE_MATTER (and optionally USE_MATTER_BLE) runs on RP2350 only and needs at least 4 MiB flash, which the Pico 2 W provides. RP2040 is rejected. See Matter.

    Enable either in a personal build configuration and test on your board; compilation does not establish radio operation or Wi-Fi coexistence.

    Hardware testing¶

    An exact Pico 2 W smoke test has passed: factory write with read-back verification, reset/USB CDC reconnect, LittleFS mount/read, settings persistence, Wi-Fi/NTP startup, HTTP, browser UI, and web-console operation.

    Still open: backup/restore, recovery, interrupted-update behavior, and broader testing. What each wired operation writes is described in Build System Internals.
