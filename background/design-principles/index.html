    Design Principles¶

    How Newmota is built, in one page: the same portable application runs on five chip families by talking only through small native platform adapters — no Arduino layer, direct vendor SDKs. Contributors start here; users only need the takeaway that daily behavior (commands, web UI, templates) is identical everywhere, while flashing and recovery differ per chip.

    Architectural Principles¶

    1. Zero Host Fallback & Zero Arduino Core¶

    Newmota compiles directly against vendor SDKs (ESP-IDF, BouffaloSDK, LibreTiny framework-beken-bdk, Ameba RTOS). It does not use Arduino abstraction layers, host compiler mocks, or third-party application frameworks.

    2. Platform Admission Requirement¶

    Sub-2 MiB physical flash devices are excluded from scope. Every target platform must provide at least 2 MiB of physical flash to run Newmota.

    3. Public Platform Contract¶

    Portable code (src/app/) never includes native SDK headers directly. All platform interactions pass through src/platform/include/newmota/platform/ headers and the newmota::platform namespace: - System boot and shutdown lifecycle hooks. - System ticks and high-resolution timer access. - Console UART input/output (single application console for logs + commands). - Flash partition access and LittleFS VFS binding. - Native digital GPIO, Wi-Fi station, restart/safeboot mechanics, and (on ESP) the RTC fast-restart guard.

    4. Native Entry Points¶

    Each platform owns its native startup entry point under src/platform/<platform>/native/: - Initializes vendor RTOS / hardware peripherals. - Mounts storage partitions. - Hands execution over to newmota::app::run().

    Porting References¶

    Newmota migrates Tasmota behavior in small, independently buildable and testable slices:

    1. Tasmota is the primary behavioral and implementation reference. Every feature slice begins by reviewing the relevant Tasmota documentation and current source — even when Newmota will refactor substantially. The review identifies the compatibility contract, useful behavior, edge cases, and prior tradeoffs. Tasmota source is not copied as is; intentional differences and their rationale are recorded, and the Tasmota review remains a mandatory regression check.
    2. ESP-IDF is the leading Newmota implementation platform and the reference for common platform decisions. Other platforms normally follow the portable Newmota contract and the existing ESP-IDF/Newmota implementation.
    3. Fallback baseline: when neither Newmota nor Tasmota supplies a suitable implementation or configuration, the ESP-IDF/Tasmota configuration for the matching flash class is the default starting baseline — including partition layouts where practical. Native SDK boot constraints, image formats, alignment, reserved regions, and hardware evidence may require a deliberate deviation; the deviation is adapted deliberately and recorded rather than copied or guessed.

    Resource Profiles¶

    Resource profiles are target build presets that define the feature set compiled into the binary.

    Profile Target Flash Class Default Feature Surface Initial Targets
    Compact 2 MiB Flash Mandatory device-hosted web server + essential UI (HTTP+Gzip on port 80), bounded plain MQTT, LittleFS storage where the selected layout preserves it (Beken's OTA overlay may be erased), serial provisioning, basic I/O, Berry (mandatory in normal app builds). esp32c2-2m, pico-w, bl602-2m, cb2s-2m, bw16-2m
    Standard 4 MiB Flash All Compact features with more flash headroom: the crypto set Matter needs on ESP, and optional drivers (sensors, energy meters, WS2812, display). The web UI stays HTTP+Gzip by default; USE_WEB_HTTPS: true opts in. ESP32-C3/S3 reference, pico2-w
    Large 8 MiB+ Flash All Standard features, with HTTPS+Brotli web UI on port 443 (per-device self-signed certificate) enabled by default. Display, LVGL, and I2S audio are optional features that need the flash headroom. ESP32-P4, ESP32-S31, esp32s3-qio-opi-8m-8m
    Safeboot Recovery partition budget from the platform layout Minimal recovery image without the normal UI, Berry, time service, timers, or dev self-tests; carries a stripped authenticated HTTP+Gzip recovery page with a bounded application-image updater. Selected only by a safeboot-role environment, never a board default. bw16-2m-safeboot, esp32s3-qio-qspi-safeboot, bl602-2m-safeboot, pico-w-safeboot, pico2-w-safeboot

    Warning

    The profile follows the flash size on every platform: 2 MiB environments are Compact, 4 MiB environments Standard, and environments with 8 MiB or more Large. The one exception today is esp32h2, a 4 MiB environment with the Compact profile. make list shows the profile of every environment.

    Feature selection and experimental surfaces¶

    A feature compiled into a profile and a feature enabled by default are different things. BLE (USE_BLE, USE_BLE_SENSORS) and Matter (USE_MATTER, USE_MATTER_BLE, USE_MATTER_BRIDGE) are implemented but no checked-in profile selects them; enable them in a personal build and test on your hardware. See Personal Build Configurations.
