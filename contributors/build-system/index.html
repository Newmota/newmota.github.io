    Build System Internals¶

    Newmota provides a single, unified command interface driven by a top-level Makefile and Python build orchestration scripts (tools/newmota/). This page is contributor reference — if you just want firmware for your device, see Install & Update Firmware.

    Core Architecture¶

    Rather than relying on separate build systems for each micro-controller vendor, Newmota defines a common pipeline interface that maps platform-specific setup, configuration, compilation, and packaging tasks into standardized execution steps.

    flowchart LR
    User["Developer / CI"] -->|make env| Makefile["Top-Level Makefile"]
    Makefile -->|python -m newmota| Driver["Build Orchestration Driver"]
    Driver --> Catalog["Catalog Resolver<br/>(chips, boards, envs)"]
    Driver --> PlatformAdapter["Platform Adapter<br/>(platforms/esp, pico, bouffalo, beken, amebad)"]
    PlatformAdapter --> NativeSDK["Native Upstream SDK Build System"]

    make forwards to the unified python -m newmota CLI (tools/newmota/__main__.py). Each platforms/<platform>/ directory owns its build.py (setup/build), images.py (layout/packaging), and device.py (programmer protocol) — see the source layout and the build-tool ownership guide linked there.

    Command Interface Summary¶

    Command Description
    make uv-setup Creates and synchronizes Python virtual environment with uv.
    make list Lists all configured chips, boards, and environments.
    make config Opens the interactive configurator, writes a personal user_config/<name>.yaml, and can build it.
    make validate-catalog Runs comprehensive validation on declarative configuration files.
    make setup ENV=<name> Installs missing cross-compiler toolchains and SDK dependencies for a target.
    make setup PLATFORM=<name> Installs toolchains for an entire platform cohort (esp, pico, bouffalo, beken, amebad, all).
    make sdk-check Verifies the installed SDKs (release archives or .sdk/ checkouts) against the pins in config/sdk/.
    make sdk-fetch Downloads every pinned SDK release archive, for offline builds.
    make sdk-checkout SDK=<key> Clones a pinned SDK into .sdk/ for SDK patch work; builds then use that checkout.
    make <environment> Builds a specific target environment (e.g. make esp32c2-2m, make pico2-w).
    make build BOARD=<name> Builds any native board recipe on demand (e.g. make esp32s3-qio-opi).
    make test Builds the five-entry cross-platform routine test matrix (esp32c2-2m, bl602-2m, cb2s-2m, bw16-2m, pico2-w).
    make test-host Runs host-side crypto KAT suites and Berry VM across all, partial, and no-crypto build profiles. Does not require device hardware.
    make all JOBS=8 Builds every environment defined under config/env/ (including all ESP-IDF targets).
    make clangd ENV=<name> Generates editor compilation database for target.

    Device Operations in Detail¶

    Every device command validates the package manifest and all SHA-256 hashes before it opens a serial connection.

    What make update writes¶

    make update is the short wired development cycle — it is not the signed remote OTA implementation. It is implemented for ESP-IDF and has wired paths for Beken, AmebaD, Bouffalo, and Pico:

    • ESP-IDF: invokes the application-only build and writes only app0; bootloader, partition table, Safeboot, OTA-selection data, and LittleFS are neither rebuilt nor written.
    • AmebaD: runs the SDK's coupled KM0/KM4 build and writes only the combined application image to OTA2. That SDK build may regenerate boot-image side outputs, but make update does not write them and does not build Safeboot or a filesystem package. Since boot selection is preserved, a device currently in Safeboot remains there.
    • Beken: writes only the stock OTA staging region, whose native overlap with LittleFS is deliberate and may erase the overlay; NET/RF/BLE-bonding metadata remains outside that write. Uses bk7231tools for probing, backup, aligned write/verify, and reboot.
    • Bouffalo: rebuilds the single application image and writes only the application FW slot; boot2, both partition-table copies, Safeboot, vendor regions, and LittleFS are neither rebuilt nor written, and the FW active index is preserved so a device in Safeboot stays there. Uses the pinned blflashcommand package with the loader's SHA-256 verification.
    • Pico: rebuilds the single application image and writes only the application slot at its XIP bus address after validating the installed Newmota table; its embedded copy of that table is rewritten with the image, while Safeboot, LittleFS, the marker, and the E10 reserve are untouched (marker preserved). Uses the pinned picotool CLI with per-component read-back verification; the board must be in BOOTSEL mode.

    ESP flash capacity¶

    ESP flashing probes the actual capacity. A device smaller than the package is rejected. For a larger device, Newmota regenerates a temporary partition table with ESP-IDF's official generator and grows only the final filesystem partition; fixed offsets and the package contents remain unchanged during flashing. Probe data and the exact write plan are retained under build/work/<environment>/flash/<size>/.

    Upgrade 1 transport¶

    • Transport: Accepts direct HTTP 200 responses with an explicit Content-Length. HTTP redirects, chunked transfer encoding, and HTTPS are deliberately rejected.
    • Native Writers: Streams chunks directly to the alternate partition or OTA writer without buffering the image in RAM. Image slot sizes are validated before writing.
    • Progress Tracking: Querying Upgrade reports real-time transfer progress and final verification status.

    Parallel Build Acceleration¶

    Native SDK adapters automatically pass parallel job flags (JOBS=N or make -j) to sub-builders that support concurrent compilation (such as CMake or Ninja).

    If ccache is found in the host system's PATH, platform build adapters prepend ccache to compiler invocations automatically.

    SDK Logging (SDK_LOG_LEVEL)¶

    Every native build uses the global SDK_LOG_LEVEL setting, resolved at build time and translated into each native SDK's configuration. It defaults to warn and accepts none, error, warn, info, debug, or verbose:

    make build ENV=esp32c2-2m SDK_LOG_LEVEL=none

    Newmota's own logging stays on its platform console, so none only removes SDK diagnostics — useful for flash-size measurements. Change the single Make variable default when the project policy changes; no alternate build target is required. (BL602, BL616, and BL618DG Safeboot images always use none to fit their recovery partitions. The Beken mapping is provisional: the CB2S test build shows no meaningful size reduction with none, so its SDK log elimination is not yet treated as proven.)

    Build lifecycle stages¶

    Every firmware build executes an explicit, standardized 7-stage lifecycle managed by tools/newmota/pipeline.py.

    graph LR
    S1[1. Resolve] --> S2[2. Prepare]
    S2 --> S3[3. Configure]
    S3 --> S4[4. Pre-Build]
    S4 --> S5[5. Build]
    S5 --> S6[6. Post-Build]
    S6 --> S7[7. Package]

    Stage 1: resolve¶

    Resolves target environment parameters from config/env/<platform>/<role>/, config/boards/, and config/chips/. Determines role (application or safeboot), chip family, physical flash capacity, console UART assignment, SDK path, and required toolchain versions. If an application declares a safeboot: companion, it resolves and queues the safeboot build first.

    Stage 2: prepare¶

    Verifies toolchain and SDK readiness. If toolchains or the SDK release archive are missing, lazy setup triggers automatically to download pinned tools without failing the build.

    Stage 3: configure¶

    Merges immutable chip SDK defaults (config/build/<platform>/<chip>/) with board configuration and environment profile parameters, generating target build files inside build/work/<environment>/config/.

    Stage 4: pre-build¶

    Prepares stage build directories, pre-compiles LittleFS partition binaries (filesystem.bin) using littlefs-python, and generates C++ header files containing firmware version metadata.

    Stage 5: build¶

    Invokes the native cross-compiler toolchain and native SDK build runner (CMake, Ninja, or Makefile). Compiles application code (src/app/) and platform bindings (src/platform/<platform>/) into object files and executable binaries.

    Stage 6: post-build¶

    Invokes platform-specific binary processors: - ESP-IDF: Generates application, bootloader, and partition table images via esptool. - Raspberry Pi Pico: Generates newmota.elf, newmota.bin, and drag-and-drop newmota.uf2 binaries, embedding the application-owned partition table at build time (ELF path). - Bouffalo: Runs bflb_fw_post_proc --ptfile against the Newmota-decided TOML for partition-aware application + Safeboot boot images. - Beken: Produces the native AXF/raw diagnostic image, the CRC-wrapped application RBL for wired flashing, and the compressed/encrypted RBL for single-image OTA staging. - AmebaD: Assembles dual-core KM0 and KM4 binaries into combined bootloader and application images.

    Stage 7: package¶

    ESP-IDF builds create a checksummed development factory package; Bouffalo and Pico builds create paired factory packages plus wired application-only update paths; Beken builds create target-validated factory and stock-OTA artifacts; and the AmebaD bw16-2m build creates a paired factory package plus a wired OTA2 update path. ESP-IDF signed OTA and all other platform release/deployment paths remain untested.

    For packaging platforms, an immutable development factory package is written under build/firmware/<environment>/<version>/ containing: - Merged factory flash images (ESP-IDF), paired Safeboot + application FW images with boot2/tables (Bouffalo) or marker-aware slots (Pico), RBL factory + stock-OTA artifacts (Beken), or the paired Safeboot + application image2 outputs, boot images, LittleFS image, and flashloader (AmebaD). - Offset-addressed individual component binaries. - Immutable package manifest.json recording build timestamps, board parameters, git revisions, tool versions, role metadata, and SHA-256 hashes of all binary outputs. Platforms without a packaging path fail closed rather than generating misleading packages.

    One BuildDateTime value (YYYY.MM.DD HH:MM:SS) is generated per build invocation and shared by every image in that build — application and Safeboot companions carry the same stamp, embedded in PlatformInfo (surfaced as StatusFWR) and recorded in the manifest. The local build timezone is used by default; setting SOURCE_DATE_EPOCH produces a reproducible UTC timestamp instead.

    Rebuilding an existing environment and version combination that results in different output bytes is treated as an explicit error to maintain build reproducibility and packaging integrity.
