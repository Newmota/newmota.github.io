    Source & Config Reference¶

    Reference for contributors: where firmware configuration lives, how the source tree is organized, and what a build produces. End users don't need this page — see First Steps and Daily Use instead.

    Configuration catalog (config/)¶

    Newmota uses a declarative catalog model to define supported microcontrollers, target board recipes, firmware environments, SDK settings, and partition layouts.

    The configuration hierarchy lives under config/, with local configurations in user_config/ and browser locales in language/:

    config/
├── chips/        # Public chip declarations and capabilities
├── boards/       # Hardware recipes (chip, flash, PSRAM, console UART)
├── env/          # Firmware build policies and matrices
├── build/        # Immutable vendor SDK default configurations
├── hardware/     # Frozen GPIO function IDs, pin topologies, product modules, display descriptors
├── sdk/          # SDK & host-programmer version pins, plus ESP-IDF Python constraints
└── partitions/   # Native partition layouts keyed by flash size

user_config/      # Ignored personal environments (inherit: <base-id>)
language/         # Build-time browser locale catalogs (en_GB.toml, de_DE.toml)

    1. Chip Catalog (config/chips/<platform>/)¶

    Maps a public chip identifier (e.g. esp32c2, rp2350, bl602, bk7231n, rtl8720dn) to its native SDK target, processor architecture, flash interfaces, and baseline capabilities.

    2. Board Recipes (config/boards/<platform>/)¶

    Defines native physical hardware recipes (e.g. pico2-w.json, esp32s3-qio-qspi.json). A board recipe specifies: - chip: The target chip identifier. - flash: Physical flash memory capacity (size_kb), bus mode (qio, dio), and speed (frequency_mhz). - psram: Optional PSRAM memory size, bus mode, and clock frequency. - console: Active console peripheral (uart0, usb-cdc, or usb-serial-jtag). - profile_default: Assigned resource profile baseline (Compact, Standard, Large, Safeboot).

    3. Environment Specifications & Explicit Roles (config/env/<platform>/<role>/)¶

    Defines complete, buildable firmware environment targets. Environments are partitioned into explicit role directories:

    • application/: Primary application firmware images.
    • safeboot/: Minimal recovery firmware images built to perform emergency recovery or staging.
    # config/env/esp-idf/application/esp32s3-qio-qspi.yaml
name: esp32s3-qio-qspi
board: esp32s3-qio-qspi
role: application
profile: Standard
safeboot: esp32s3-qio-qspi-safeboot
language: en_GB

    Applications can explicitly declare their paired safeboot dependency (safeboot: <env>). When an application specifies a safeboot companion, the build pipeline automatically builds and packages the safeboot image before packaging the application. Current pairs: esp32s3-qio-qspi → esp32s3-qio-qspi-safeboot, bw16-2m → bw16-2m-safeboot, bl602-2m → bl602-2m-safeboot, pico2-w → pico2-w-safeboot, pico-w → pico-w-safeboot. Beken has no safeboot environments by design; cb2s-2m, cb3s (BK7231N), and xh-cb3s (BK7238) are application-only.

    config/env/matrices/
└── test.txt     # Routine cross-platform test matrix (4 Compact + 1 Standard target)

    4. Immutable SDK Defaults (config/build/<platform>/<chip>/)¶

    Contains native vendor SDK default settings: - ESP-IDF: sdkconfig.defaults (and platform-common settings in common/sdkconfig.defaults). - Pico SDK: Native cmake.defaults definitions. - Bouffalo / Beken / AmebaD: Native defconfig files.

    During a build, Newmota merges these defaults with board requirements and environment flags into build/work/<environment>/config/. Checked-in defaults and the SDK sources are never modified.

    5. SDK & Toolchain Version Pins (config/sdk/)¶

    Stores human-readable version declarations for SDKs and host tools (esp-idf.toml, esp-idf-v6.1.toml, pico-sdk.toml, bouffalo.toml, beken.toml, amebad.toml). These files declare: - Upstream release label and exact Git commit hash. - Toolchain releases and download URLs. - External tool archive SHA-256 checksums.

    6. Partition Definitions (config/partitions/<platform>/)¶

    Contains partition tables keyed by total physical flash capacity: esp-idf/{2,4,8,16}m.csv (exact Tasmota schemes), bouffalo/2m.toml (BL602 asymmetric FW slots + dedicated LittleFS) and bouffalo/4m-{bl602,bl616,bl618dg}.toml (target-specific application/Safeboot slots + LittleFS), beken/{2m,2m-bk7238,4m}.toml (native OTA envelope with LittleFS tail overlay), amebad/2m.toml, pico-sdk/4m-rp2350.json (official picotool JSON for RP2350), and pico-sdk/2m-rp2040.json (project-owned checked layout for RP2040). Immutable native SDK defaults live in config/build/<platform>/<chip>/; each build resolves those defaults with its board and environment settings into build/work/<environment>/config/ without modifying the SDK checkout. Board and chip files never contain partition or filesystem allocation fields. Beken has no Safeboot or alternate-image layout by design.

    Partition and native-configuration choices follow the porting reference hierarchy: an existing Newmota implementation is preferred, otherwise the ESP-IDF/Tasmota configuration for the matching flash class is the default starting baseline where no stronger platform-specific reference exists. Native SDK boot constraints, image formats, alignment, reserved regions, and hardware evidence may require a deliberate deviation, which is recorded with the resulting layout.

    Catalog Validation (make validate-catalog)¶

    Newmota includes a catalog validation step (tools/newmota/catalog.py) that checks the consistency of all JSON/YAML configuration files without invoking compilers or downloading SDKs.

    make validate-catalog

    Validation checks include: - Cross-references between chips, board recipes, and environment files. - Consistency of partition table total flash allocations. - Integrity of SDK pin declarations against expected structure. - Compatibility of target-specific memory and console UART choices.

    Source tree (src/)¶

    The Newmota repository layout separates portable application code, platform adapters, build tools, configuration files, and upstream vendor SDK checkouts. Portable code lives in src/app/; platform implementations and their native SDK integration live together under src/platform/ behind a small public contract. There is no host compiler fallback — every build compiles through a platform's native SDK.

    src/
├── app/                        # Portable C++ application code
│   ├── core/                   # Portable application mechanisms
│   │   ├── app.cpp             # Main application state machine & entry point
│   │   ├── log.cpp             # Portable logging implementation
│   │   ├── scheduler.cpp       # Cooperative task scheduler
│   │   ├── message/            # Message router & canonical state routing
│   │   ├── command/            # Central command processor & synchronous chains
│   │   ├── hardware/           # GPIO resolver, runtime, hardware commands
│   │   ├── storage/            # Storage abstractions & filesystem commands
│   │   └── system/             # System control & reboot commands
│   ├── services/               # Portable application services
│   │   ├── settings/           # Persistent LittleFS settings (settings.a/b)
│   │   ├── status/             # Status, StatusPRM/FWR/LOG/MEM/NET/MQT/TIM/SNS/PTH/STS
│   │   ├── energy/             # Energy instances, accounting, commands, protection
│   │   ├── telemetry/ temperature/ # Telemetry routing and global temperature owner
│   │   ├── power/              # Relays/buttons/LEDs (Power, PowerOnState, PulseTime, …)
│   │   ├── light/              # 1- to 5-channel PWM & WS2812 lights (Dimmer, Color, CT, White, HSB)
│   │   │   └── berry/          # Global Berry light module binding & gamma helpers
│   │   ├── mqtt/               # Bounded plain MQTT client, codec, wire, settings
│   │   │   └── berry/          # Berry mqtt module
│   │   ├── ble/                # BLE scan controls shared by the native adapters
│   │   ├── matter/             # Matter node, commissioning, bridge and Berry API
│   │   ├── timers/             # 16 persistent civil & solar timers (Timers, Timer1..16, Latitude, Sunrise)
│   │   ├── update/             # Asynchronous OTA URL pulls & native writers
│   │   ├── berry/              # Berry VM service, /autoexec.be, global newmota object
│   │   │   └── modules/        # newmota, crypto, gpio, serial, persist, path, pixmat, lvgl, display, audio, energy, led_strip, wire, BLE
│   │   ├── network/            # Station Wi-Fi, SoftAP onboarding, Ping, wget

│   │   ├── migration/          # Tasmota 15.5.0.2 settings importer for ESP targets
│   │   └── web/                # HTTP/HTTPS UI service, light/GPIO/timer/MQTT/firmware pages, file editor, dual consoles
│   │       └── berry/          # Berry widget module
│   ├── drivers/
│   │   ├── io/basic_io.cpp     # Relay/LED/button physical I/O driver

│   │   ├── led_strip/          # WS2812 RGB/RGBW addressable LED strip driver
│   │   ├── energy/             # Meter drivers (CSE7766, PZEM, BL09xx, ADE79xx, Modbus, …)
│   │   ├── modbus/ adc/ spi/ gpio/ io_expander/ # Shared RTU, ADC, device SPI, and GPIO owners
│   │   ├── sensors/            # Environmental, BLE and sensor-history owners (BME280, BH1750, DHT, BLE sensors)

│   ├── gpio_topology.cpp       # Shared topology helper
│   ├── lwip/tcp_stream.cpp     # Portable raw-TCP stream adapter for lwIP
│   ├── esp-idf/                # ESP-IDF adapter (console, filesystem, Wi-Fi, RTC guard, web, pwm…)
│   ├── pico-sdk/               # Pico SDK adapter (RP2350/RP2040, filesystem, boot_select, pwm…)
│   ├── bouffalo/               # BouffaloSDK adapter (filesystem, sdk_log.h, pwm…)
│   ├── beken/                  # Beken BDK adapter (filesystem, flash_access, pwm, rbl_update…)
│   └── amebad/                 # AmebaD RTOS adapter (dual-core, filesystem, network, pwm…)

    ├── littlefs/               # ARM LittleFS 2.x
    └── tamp/                   # Tamp compression

    Future non-physical features belong in src/app/services/, hardware-facing implementations in src/app/drivers/. Those groupings already exist; new subdirectories are created only when they contain code.

    Build tooling (tools/newmota/)¶

    make is the public interface; it forwards commands to PYTHONPATH=tools python -m newmota (unified CLI in __main__.py with lazy dispatch). Ownership rules live in the build-tool ownership guide, tools/README.md in the Newmota repository: shared orchestration selects a platform through the platforms registry and never imports a platform implementation directly; a platform may import shared modules and its own helpers, but never another platform.

    tools/newmota/
├── __main__.py         # Unified CLI: argument parsing + lazy command dispatch
├── catalog.py          # Catalog parsing, board schema, validation orchestration
├── config.py           # Native config layering and identity (sdkconfig/defconfig/cmake)
├── pipeline.py         # Selection, dependency ordering, lifecycle, native manifest
├── package.py          # Manifest safety, layout facts, empty LittleFS images
├── device.py           # Device contract, port selection, device workflows
├── host.py             # Processes, SDK pins, toolchains, common staging helpers
├── features.py         # Common feature policy, dependencies, source ownership
├── berry.py            # Berry generation and incremental inputs
├── web.py              # Deterministic Gzip/Brotli embedding of the web UI asset
├── i18n.py             # Locale catalog validation and rendering
├── ota.py / audio.py / crypto.py / lvgl.py / energy_inventory.py # Feature-specific build helpers
├── compdb.py           # Compilation database collection and activation
├── hardware.py / topology.py # Hardware catalog + topology resolution helpers
└── platforms/          # One explicit, lazy platform registry (__init__.py)
    ├── esp/            # Public selector esp; native SDK dir esp-idf
    │   ├── build.py    # Setup, requirements/target checks, build adapter
    │   ├── images.py   # Layout resolution, image checks, packaging, Safeboot checks
    │   ├── device.py   # Programmer protocol, write bounds, verification, monitoring
    │   └── usb_monitor.py # USB-safe no-reset serial monitor launcher
    ├── bouffalo/       # build.py / images.py / device.py (blflashcommand path)
    ├── beken/          # build.py / images.py / device.py + specialists:
    │                   # bdk.py, codec.py, profile.py (profile shared, dependency-free)
    ├── amebad/         # build.py / images.py / device.py + uploader.py
    └── pico/           # Public selector pico; native SDK dir pico-sdk
                        # build.py / images.py / device.py (picotool path)

    Build outputs (build/)¶

    Build artifacts are generated under build/ and ignored by version control:

    build/
├── clangd/             # Generated per-environment compile_commands.json
├── firmware/           # Packaged development factory images & manifests
│   └── <environment>/
│       └── <version>/
│           ├── manifest.json   # Immutable manifest: timestamps, board params,
│           │                   # git revisions, tool versions, roles, SHA-256 hashes
│           ├── factory.bin     # (ESP-IDF) combined factory flash image
│           └── filesystem.bin  # Pre-generated LittleFS partition image
└── work/               # Staged SDK build dirs, native objects, checkummed manifest
    └── <environment>/
        ├── config/     # Resolved native SDK build configs
        └── flash/<size>/ # Probe data + exact write plan for larger flash chips

    Native SDK work and its checksummed build manifest live under build/work/<environment>/ — these are not automatically deployable firmware. All five platform packagers (ESP-IDF, Bouffalo, Beken, AmebaD, Pico SDK) write their manifest, factory components, layout source, and debug files under build/firmware/<environment>/<version>/ and never mislabel the application binary as OTA firmware. Rebuilding the same environment/version replaces the generated package; rebuilding with different output bytes is an explicit error.
