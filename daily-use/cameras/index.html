    Cameras¶

    Camera support is optional and hardware testing is open. Both camera features require a board with PSRAM and a Berry sensor driver loaded from the filesystem or built into the firmware. The features are mutually exclusive:

    • USE_WEBCAM supports JPEG-producing DVP sensors on ESP32-S3, ESP32-P4 and ESP32-S31. The source repository provides an OV2640 driver and an ESP32-S3-EYE example.
    • USE_CSI_WEBCAM supports MIPI-CSI sensors on ESP32-P4, with OV5647, IMX219 and OV02C10 drivers. Upload the matching ISP tuning file as /isp.json where available; OV02C10 has no ISP tuning yet.

    The drivers live in berry/drivers/camera/, with ISP tunings in its isp/ directory. A personal build can also put drivers, tuning files and autoexec.be into the factory filesystem.

    Select the feature in make config or a personal build, configure the sensor's I2C and camera pins as appropriate, upload its Berry file, and start it from autoexec.be, for example load("ov2640.be") cam.register(OV2640()). A personal build can instead build the driver class in with solidify, so autoexec.be only registers it. Use Webcam to inspect the state and WcStream 1 to enable the server on port 81.

    The server offers /snapshot.jpg and /stream for JPEG snapshots and MJPEG. It has no password; restrict access to a trusted network. Up to three MJPEG viewers can connect, and the stream shares port 81 with the I2S audio listener. An HTTPS browser page may block the embedded HTTP stream; use its link instead.

    WcResolution, WcQuality, WcMirror and WcFlip control capture; WcStats reports frame counters. WcInit restarts capture and WcStop stops it. Berry scripts can use camera.info() and camera.snapshot(), although snapshots larger than Berry's 32 KiB bytes limit must be fetched over HTTP.

    On CSI, WcSession selects MJPEG (1), H.264 over RTSP and WebSocket (2), or LAN WebRTC (3). Optional USE_CSI_STILL adds full-sensor JPEG stills (4), with substantial PSRAM requirements. CSI resolution and JPEG availability depend on the sensor, P4 silicon revision and SDK. See the firmware repository's src/app/drivers/camera/README.md for wiring, commands, sensor setup and limitations.

    CSI supports digital pan and tilt with WcPan, WcTilt and WcPosition when the capture window is smaller than the sensor. The Home camera card provides directional controls where movement is possible. This shifts the window without zooming, and the position resets when the camera restarts. Matter camera builds can use the same viewport for digital PTZ.

    Example: ESP32-S3-EYE¶

    The ESP32-S3-EYE has an OV2640 camera, an I2S microphone, a microSD slot and a 240x240 ST7789 display. One personal build covers all four, with the camera driver built in and the display descriptor written into the factory filesystem:

    name: s3-eye
inherit: esp32s3-qio-opi-8m-8m     # 8 MiB flash, 8 MiB octal PSRAM
features:
  USE_WEBCAM: true
  USE_I2S: true
  USE_DISPLAY: true
  USE_SDCARD: true
solidify:
  - berry/drivers/camera/ov2640.be
filesystem:
  - source: config/hardware/displaydesc/ST7789_display.ini
    target: /display.ini
template: {"NAME":"ESP32-S3-EYE","ARCH":"esp32s3","GPIO":[1,1,7872,1,5024,5056,5120,5152,5090,5089,5091,5088,5092,5184,1,4992,5095,5094,5093,0,0,736,0,0,0,0,0,8800,8832,8864,7808,7840,800,768,1,1,704,992],"FLAG":0,"BASE":0}

    The template assigns:

    Part GPIO
    Camera SIOD 4, SIOC 5, VSYNC 6, HREF 7, PCLK 13, XCLK 15, D0–D7 11, 9, 8, 10, 12, 18, 17, 16
    Microphone (I2S) DIN 2, BCLK 41, WS 42
    microSD (one-bit SDIO) CMD 38, CLK 39, D0 40
    Display (hardware SPI) CLK 21, MOSI 47, CS 44, DC 43, backlight 48

    autoexec.be then only needs cam.register(OV2640()). Configure the microphone's input profile with I2SConfig as described in Audio; the template only sets its pins.

    The template owns the pins: the display descriptor is the generic ST7789 file, whose * pin fields take the template's display pins. A descriptor that names a pin the template also assigns is refused, and the log names the pin. Tasmota's template for this board puts the display on software SPI, and its auto-configuration descriptor names the pins itself; Newmota uses hardware SPI and leaves the pins to the template.

    GPIO43 and GPIO44 are UART0's pins. With the USB console, the template may take them: the USB console keeps running, and a UART0 fallback (no USB host at boot) stops until restart. Boot messages still appear on UART0 during reset.

    Example: Matter camera on an ESP32-P4 before revision 3¶

    A Matter camera needs CSI, so it runs on the ESP32-P4. For a board with silicon before revision 3.0, inherit esp32p4; revision 3 boards use esp32p4r3 or esp32p4x:

    name: p4-matter-cam
inherit: esp32p4
features:
  USE_MATTER_CAMERA: true    # selects USE_MATTER_TCP, USE_CSI_WEBCAM and USE_AUDIO_OPUS
  USE_WIFI: true             # through the ESP-Hosted companion

    Load the sensor driver and its ISP tuning as above, and commission the device as described in Matter. Video uses H.264. Before revision 3, the camera produces JPEG only in the MJPEG session on ESP-IDF 5.5, and not at all on ESP-IDF 6.1, so Matter snapshots are not available while video streams. This example therefore leaves out USE_CSI_STILL. The Matter camera has not yet been tested against a controller.
