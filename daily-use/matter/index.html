    Matter¶

    Matter lets a controller such as Apple Home, Google Home, Home Assistant or SmartThings operate your device directly, without MQTT or a vendor cloud. Newmota's Matter stack is optional, off by default, and work in progress: it has reached a first commissioning, but broad controller and hardware coverage is not yet tested.

    What it does¶

    • Builds a Matter node from the hardware that is already configured on the device.
    • Supports on-network commissioning, and BLE commissioning on ESP-IDF and RP2350 when the BLE features are selected.
    • Exposes lights, relays and environmental sensors to the controller.
    • Can bridge remote Tasmota devices over MQTT with USE_MATTER_BRIDGE.
    • Keeps fabrics, sessions and subscriptions across a restart.

    Requirements¶

    Item Requirement
    Platform ESP-IDF, RP2350 (Pico 2 W) or Beken; RP2040 is rejected
    Flash At least 4 MiB; 2 MiB on Beken
    Build features USE_MATTER (selects Berry and Wi-Fi)
    Entropy A platform hardware entropy source
    Runtime switch SetOption151 1, then restart

    No checked-in profile selects Matter. Switch it on in make config, or enable it in a personal build configuration by hand:

    name: my-matter
inherit: esp32s3-qio-qspi
features:
  USE_MATTER: true

    Add the optional pieces you need:

    features:
  USE_MATTER: true
  USE_MATTER_BLE: true      # BLE commissioning (also selects USE_BLE)
  USE_MATTER_BRIDGE: true   # remote Tasmota devices over MQTT (also selects USE_MQTT)

    Example: a Beken plug with a fixed pairing code¶

    On Beken, Matter fits 2 MiB without MQTT. An XH-CB3S (BK7238) was commissioned with chip-tool and Apple Home; no CB2S has been tested yet. Turning off the web console, the file browser and Berry gpio gives a smaller page and image; the Template and Module tabs stay available:

    name: matter-plug
inherit: xh-cb3s
device_name: Plug
features:
  USE_MATTER:
    passcode: 20202021       # choose your own
    discriminator: 3840
  USE_MQTT: false            # required on Beken: the image must fit the update area
  USE_WEB_CONSOLE: false
  USE_WEB_FILESYSTEM: false
  USE_BERRY_GPIO: false

    Without settings, USE_MATTER: true picks a random passcode and discriminator on first start. Fixed values are accepted only in user_config/; the code is then readable in the firmware image and the same on every device flashed with it. The build prints the QR code, its payload and the pairing code. A Matter camera needs an ESP32-P4; see the camera example.

    USE_MATTER selects the crypto primitives the stack needs (SPAKE2P, AES-CCM and their dependencies). The Berry classes are solidified into flash at build time, so they cost no heap until the Matter VM names them.

    Commissioning¶

    1. Set the option and restart:
    > SetOption151 1
{"SetOption151":"ON"}
> Restart 1

    1. After Wi-Fi connects, the log prints the pairing code and QR content. On a device with no fabrics, the commissioning window stays open for 15 minutes.

    2. Open the controller's "add device" flow and enter the pairing code, or scan the QR code from the Matter card on the Home page. The card appears while Matter is running:

    3. While a window is open it shows the number of fabrics, the pairing code and a QR code.

    4. Otherwise it offers Open commissioning window.

    5. Remove all fabrics is available once a controller has joined; it needs a second press.

    6. From Berry you can open a window yourself. The argument is the window length in seconds:

    Br print(_matter.pairing_code())
Br _matter.open_basic_window(900)

    With USE_MATTER_BLE and USE_BLE, a device that has no fabrics and no Wi-Fi also advertises for BLE commissioning, 20 seconds after start and until the window closes. The BLE stack stops afterwards. A Berry script must not use BLE connection callbacks while this runs. Wi-Fi credentials supplied by the commissioner stay in RAM until commissioning completes. If the fail-safe expires after a tested network, the device restarts and returns to its stored state. Access-point onboarding stays available and whichever finishes first wins.

    What the node contains¶

    The node is rebuilt from the hardware at every start, in the order lights, relays, sensors:

    • Each light becomes an on/off, dimmable, colour-temperature or extended-colour light, depending on what light.get() reports. Move, Step and move-to commands with a transition time advance on the stack's 250 ms tick, or once a second for bridged lights, and RemainingTime reports what is left. An off light ignores level and colour commands unless ExecuteIfOff is set.
    • Each remaining POWER output becomes an on/off plug-in unit.
    • Each temperature, humidity, pressure and illuminance value in Status 10 becomes a sensor, read when a sensor reports a new value, at most every 2 seconds. A sensor that appears after start waits for the next restart.
    • A board with none of these gets one virtual on/off output so commissioning can be tested.

    Relays and lights changed outside Matter reach controllers on the next 250 ms tick. The tick compares the change counter of the power owner and runs no command while it stands still. Bridged devices are followed when their state message arrives.

    Commands¶

    Matter commands answer only while the stack runs; otherwise they return {"<command>":"Off"}.

    Command Effect
    MtrInfo Fabrics, endpoints with device types, enforcement, window, and — while open — the pairing code and QR content
    MtrJoin 1 opens a commissioning window, 0 closes it, no argument queries
    MtrReset 1 Removes every fabric (all controllers are forgotten) and opens a window

    Tasmota's MtrUpdate does not exist yet.

    Bridging remote Tasmota devices¶

    With USE_MATTER_BRIDGE, up to seven remote Tasmota devices appear as bridged endpoints over MQTT. Configure them from the console; changes take effect at the next restart:

    Br _matter.bridge.discover(true)            # Listen to tasmota/discovery/#
Br print(_matter.bridge.discovered.keys())  # Discovered device ids, a few seconds later
Br _matter.bridge.add_discovered("<id>")    # Relays, lights and sensors from discovery data
Br _matter.bridge.discover(false)
Br _matter.bridge.add("topic", [{'type': 'relay', 'relay': 1}]) # Without discovery
Br _matter.bridge.remove("topic")

    Newmota publishes Home Assistant discovery, not Tasmota discovery, so Newmota remotes need add. Commands fail while a remote is unreachable or has not answered live since the last link change. An MQTT publication above the packet limit is skipped with a log line instead of ending the session.

    Access control and security¶

    Each fabric keeps its own access control list, and CASE certificates are checked against the fabric root. For now both only log: MTR: NOC chain validation failed and MTR: ACL would deny. They do not refuse anyone yet, so a holder of a fabric's IPK can still become administrator. Once real controllers commission and operate without those lines, enforcement can be turned on:

    Br _matter.set_enforce_access(true)

    The setting survives restarts.

    The device uses Matter's test attestation certificate (vendor 0xFFF1), so controllers show it as uncertified.

    Removing the device from a controller removes only that controller's fabric. A controller that added two fabrics leaves the other one on the device, and the window stays closed until opened from the card or with MtrJoin 1.

    Storage¶

    Fabrics, the device identity, and CASE sessions with their subscriptions are stored unencrypted in /.newmota/matter/. A controller therefore carries on after a restart without a new handshake, and each resumed subscription gets a full report as soon as the network is up. Sessions reserve a range of send counters and resume above it, so a restart cannot reuse a nonce. Saving happens when a session or subscription changes and when that range runs short.

    Status¶

    Matter is young. Expect controller-specific quirks, missing optional clusters, and no hardware testing beyond a first commissioning. Access enforcement is deliberately off, and the test attestation certificate is deliberate until a production certificate path exists.
