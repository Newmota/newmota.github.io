    Wi-Fi, Time & Status¶

    Getting online, keeping the clock right, and asking the device how it's doing. The two-minute version: set SSId1/Password1, confirm with Status 5, set your Timezone — details below.

    Onboarding & Recovery Access Point (SoftAP)¶

    When a device has no stored Wi-Fi credentials, or if it cannot associate with configured networks, Newmota automatically starts an open onboarding access point:

    • SSID: Formatted as newmota-XXXXXX (derived from the device MAC address and bounded to 31 bytes).
    • Default IP: 192.168.4.1.
    • Onboarding Page: Connect your laptop or smartphone to the device's open Wi-Fi network and navigate to http://192.168.4.1/ (https://192.168.4.1/ on builds with HTTPS). There is no captive-portal DNS redirect, so type the address yourself. Every platform family, including Bouffalo BL616/BL618DG, serves the setup AP from 192.168.4.1 with DHCP.
    • Safe Credential Testing: The browser onboarding page allows you to scan local networks, select your SSID, and test credentials with the device before committing them. Credentials are saved only after successful association and DHCP lease.

    Wi-Fi Station Service¶

    Once configured, your device joins your network as a station client. Configure primary and fallback networks:

    SSId1 MyHomeNetwork
Password1 my-secret-password
SSId2 MyPhoneHotspot
Password2 hotspot-password

    Network Identity & Diagnostic Commands¶

    Command Syntax Description
    Hostname Hostname Queries the current runtime network hostname.
    IPAddress IPAddress or IPAddress<1..5> Queries all configured addresses (1: IP, 2: Gateway, 3: Subnet, 4: DNS1, 5: DNS2) or one indexed address.
    WifiScan WifiScan [1] Performs an asynchronous scan and lists detected APs (SSID, RSSI, channel, BSSID, security mode).
    WifiTest WifiTest <ssid>,<password> Tests station connection to candidate credentials without saving them or dropping existing links. Joins the first access point with that SSID it finds and gives up after 9 s, as Tasmota does (12 s on BL602).
    DeviceName DeviceName [name] Sets or queries the human-readable device name (up to 31 bytes), distinct from the runtime network hostname.
    Ping Ping <host> or Ping<0..8> <host> Runs an asynchronous IPv4 ICMP ping campaign. Ping sends 1 probe; Ping1–Ping8 send N probes; Ping0 makes up to four attempts and stops at the first reply. Querying Ping or Ping ? returns the latest campaign stats.
    wget wget <URL> Asynchronously downloads direct HTTP 200 file from URL to LittleFS (saving to the URL basename, or /index.html), atomically replacing on success. Querying wget reports progress.

    Check connection status at any time with Status 5 — the IPAddress it reports is where the web UI lives:

    > Status 5
{"StatusNET":{"Hostname":"newmota-A1B2","IPAddress":"192.168.1.50","Gateway":"192.168.1.1","Subnetmask":"255.255.255.0","DNSServer1":"192.168.1.1","DNSServer2":"0.0.0.0","Mac":"24:4C:AB:12:34:56"}}

> Ping 1.1.1.1
{"Ping":"Done"}

> Ping
{"Ping":{"State":"completed","Destination":"1.1.1.1","Sent":1,"Success":1,"Timeout":0,"Error":""}}

> wget http://192.168.1.100:8000/autoexec.be
{"wget":"Started"}

    The connected Wi-Fi band appears as Band (2.4GHz or 5GHz) in STATE, Status 5 and the web Information page after the first link refresh.

    Sleep, Wi-Fi Power & Bands¶

    Deep sleep¶

    Optional USE_DEEPSLEEP, selected in a personal build, provides timed deep sleep on all five platform families. DeepSleepTime 11..316223999 saves the interval in seconds; DeepSleepTime 0 disables it. If telemetry was disabled, enabling deep sleep sets TelePeriod 300.

    After each telemetry period the device starts a four-second countdown and sleeps until the next interval boundary on the local clock. A start other than a deep-sleep wake has a 64-second countdown, leaving time to reach the device; fifteen seconds without a network address also starts a countdown. Holding a configured DeepSleep GPIO low keeps it awake. Before sleeping, it publishes a retained tele/<topic>/DeepSleep event and closes MQTT. While deep sleep is enabled, the boot count increases only with SetOption76 1.

    ESP except C2, AmebaD and Pico retain the wake plan and correct timer slip, sleeping at most an hour at a time before returning to sleep if needed. ESP32-C2, Beken and Bouffalo do not retain it: each wait uses one sleep, limited by the chip. Beken and BL602 cap one sleep at about 36 hours. RP2040 stops its clocks except the RTC and reboots on the alarm. Tasmota's timer Wakeup rule is unavailable. These paths have not yet been tested on hardware.

    On supported ESP chips, optional USE_BERRY_ULP adds import ULP for coprocessor programs and immediate sleep; see Berry Scripting.

    Sleep¶

    Sleep 0..250 sets the dynamic loop sleep in milliseconds (default 50). The main loop aims for one pass per Sleep interval when idle, and the device keeps serving console and web input during the wait. Values above 50 are stored but act as 50, so 100 ms relay timers keep their deadlines; Sleep reports both the stored value and the active one:

    > Sleep 100
{"Sleep":{"100":{"Active":"50"}}}
    • Sleep 0 and SetOption127 1 disable Wi-Fi power saving.
    • SetOption60 1 selects normal sleep (the full wait after each pass) instead of dynamic sleep.
    • Timing-sensitive work — light fades, addressable strips, open serial ports, BLE, transfers, and builds with I2S, edge capture or a display — keeps the 1 ms loop.
    • Pico 2 W never enables Wi-Fi power saving; Beken, Bouffalo and AmebaD keep their SDK defaults.

    Status 11/STATE report SleepMode, Sleep (the applied value) and LoadAvg; Status 1 reports the stored Sleep.

    WifiPower (ESP-IDF)¶

    On ESP-IDF builds, WifiPower <dBm> sets a fixed Wi-Fi transmit power, 1 selects the chip default, and 0 follows the station's RSSI. Values above the chip maximum are capped; invalid text is rejected. The request reaches the SDK with quarter-dBm precision. Status 5 reports the resulting value.

    > WifiPower 18.5
{"WifiPower":18.5}

    Beken, Bouffalo, AmebaD and Pico builds have no WifiPower command and keep the SDK's power. Dynamic mode uses the chip default while there is no link.

    5 GHz Wi-Fi¶

    On ESP32-C5, Newmota selects the band automatically, just as Tasmota does. No field names the band: Status 11 reports Channel (36 and up means 5 GHz) and Mode, and WifiScan lists each network's channel. BW16 uses its SDK's band selection and reports Channel but not Mode. Other chips stay on 2.4 GHz. Hardware testing for both 5 GHz paths remains open.

    Timekeeping & NTP Service¶

    Accurate wall-clock time is maintained via asynchronous UDP NTP packets against standard network time servers:

    • Asynchronous Protocol: Sends non-blocking UDP requests via LwIP without pausing the main event loop.
    • Three persisted slots: NtpServer1, NtpServer2 and NtpServer3. The defaults are 2.pool.ntp.org, 2.europe.pool.ntp.org and 2.nl.pool.ntp.org.
    • No hidden fallback: only those three slots are used. Empty slots are skipped; clearing all three disables NTP while retaining the clock. Newmota does not fall back to the gateway or to randomized servers.
    • Retry Schedule: Re-queries every minute while unsynchronized; refreshes hourly once locked. A failed server moves the rotation to the next slot.
    • Manual hold: A manual Time <epoch> blocks automatic NTP and GPS updates. Time 0 releases the hold and resumes network time.
    • Format: Addresses are limited to 63 ASCII characters. Commas are accepted as dots, so NtpServer1 192,0,2,123 stores 192.0.2.123. NtpServerN 0 clears a slot and NtpServerN 1 restores its default.

    Setting features.USE_NTP: false removes the NTP client while keeping the shared clock, which is useful for an RTC- or GPS-only build.

    Time Commands¶

    Command Syntax Description
    Time Time [0 \| 1 \| 2 \| 3 \| 4 \| <epoch>] Displays current time, selects a response format (1–4), sets a manual Unix UTC epoch, or releases the manual hold with 0.
    Timezone Timezone [-13..+14 \| 99 \| +HH:MM] Sets fixed timezone offset, or 99 for automatic DST rules.
    TimeStd TimeStd <hemisphere>,<week>,<month>,<day>,<hour>,<offset> Configures Standard Time transition rule.
    TimeDst TimeDst <hemisphere>,<week>,<month>,<day>,<hour>,<offset> Configures Daylight Saving Time (DST) transition rule.
    NtpServer NtpServer<1..3> [host \| 0 \| 1] Queries all three slots or sets one. 0 clears, 1 restores the slot default.

    Time Formats¶

    Time 1–Time 4 select the persistent response format:

    • Time 1: ISO-8601 local time ("2026-09-10T22:00:00").
    • Time 2: ISO-8601 local time plus Unix Epoch seconds.
    • Time 3: numeric Unix epoch seconds (1789077600).
    • Time 4: ISO-8601 local time with millisecond precision ("2026-09-10T22:00:00.123").

    Setting SetOption52 1 appends the timezone offset decoration (for example +02:00) to valid formatted Time responses. Time 0 releases a manual hold and returns to automatic time; other values outside 1–4 are treated as a manual Unix UTC epoch and hold the clock until Time 0.

    Automatic Daylight Saving Time (DST)¶

    Setting Timezone 99 activates rule-based automatic timezone calculation:

    > Timezone 99
{"Timezone":99}

    The transition rules are configured using Tasmota's 6-parameter schema:

    $$\text{Rule} = (\text{Hemisphere}, \text{Week}, \text{Month}, \text{Day}, \text{Hour}, \text{Offset})$$

    • Hemisphere: 0 = Northern, 1 = Southern.
    • Week: 0 = Last week, 1 = First week, 2 = Second, 3 = Third, 4 = Fourth.
    • Month: 1 (Jan) to 12 (Dec).
    • Day: 1 (Sun) to 7 (Sat).
    • Hour: Hour of transition (0–23).
    • Offset: Offset in minutes from UTC (e.g. 120 = UTC+2).

    Example European Summer Time (Central European Time): - TimeDst 0,0,3,1,2,120 (Last Sunday in March at 02:00 $\rightarrow$ UTC+2) - TimeStd 0,0,10,1,3,60 (Last Sunday in October at 03:00 $\rightarrow$ UTC+1)

    Time Telemetry (Status 7 / StatusTIM)¶

    Status 7 exposes the timekeeper and its optional sources:

    > Status 7
{"StatusTIM":{"UTC":"2026-09-10T20:00:00Z","Local":"2026-09-10T22:00:00","StartDST":"2026-03-29T02:00:00","EndDST":"2026-10-25T03:00:00","Timezone":"+02:00","Sunrise":"06:45","Sunset":"19:50","Source":"ntp","Valid":true}}
    • Source is the latest accepted sample: none, manual, ntp, rtc or gps. It identifies the origin even after the network drops.
    • Valid is true once the shared clock has a trustworthy sample. Holdover keeps the civil clock valid after GPS or NTP disappears.
    • Sunrise/Sunset appear only with valid time and a non-polar date.
    • With an RTC enabled, RTC reports Chip, one-based Bus, State, Valid and the last Write result.
    • With GPS enabled, GPS reports receiver state, time, fix, position, velocity and error counters.
    • With USE_NTP_SERVER, NTPServer reports the listener's State, advertised Quality, Age, and Req/Sent/Drop counters.

    Optional RTC Chips¶

    Default-off RTC support bootstraps the shared clock and keeps UTC across power cuts. Selecting any chip enables USE_RTC_CHIPS, USE_TIME and USE_I2C on every platform family; Safeboot excludes them. Configure SCL/SDA and external pull-ups as for any I2C device.

    Feature Chip Address
    USE_DS3231 DS3231 0x68
    USE_DS1307 DS1307 0x68
    USE_BM8563 BM8563 0x51
    USE_PCF85063 PCF85063A 0x51
    USE_PCF85363 PCF85363A 0x51
    USE_RV3028 RV-3028-C7 0x52
    USE_RX8010 RX8010SJ 0x32
    USE_RX8025 RX-8025T 0x32
    USE_RX8130 RX8130CE 0x32

    USE_RX8030 is accepted as Tasmota's spelling of the same RX8130CE.

    features:
  USE_DS3231: true
  USE_NTP: false   # optional: run from the RTC alone
    • An invalid calendar can bootstrap the shared clock, but never replaces valid manual or network time and does not delay NTP.
    • Manual Time values are not written to the chip; Time 0 releases the hold.
    • Every accepted NTP sample checks the RTC; a valid calendar within two seconds is left alone, otherwise a bounded synchronous write updates it. Failed writes are retried on the next NTP sample.
    • Accepted GPS time can seed the chip immediately; successful checks wait an hour.
    • Builds reject two physical models at the same address. Alarms, temperature, SQW/CLKOUT and user RAM are outside this feature.
    • These drivers are compile-tested only; battery retention, oscillator recovery and power interruption during programming need hardware testing.

    Optional GPS (UBX)¶

    Default-off USE_GPS selects Time and the shared hardware UART owner. The receiver protocol is UBX only; the initial target is the legacy CFG-MSG/CFG-RATE interface used by u-blox 6–8 receivers, and newer generations are not tested. All platform families can select it where their native auxiliary UART supports the chosen pins; Bouffalo BL616/BL618DG cannot.

    features:
  USE_GPS: true
  USE_DS3231: true   # optional battery-backed UTC retention

    Configure exactly one GPS RX and one GPS TX with GPIO/Template, then restart. The RX variant selects the baud rate:

    Function GPIO value Baud
    GPS RX1 4352 9600
    GPS RX2 4353 19200
    GPS RX3 4354 38400
    GPS TX 4384 Same as RX

    Both directions are required (8N1), with common ground and compatible signal levels. Configured GPS pads stay reserved from Berry GPIO/serial and other owners.

    • Fresh accepted GPS time takes priority over NTP for five seconds after each sample; NTP resumes when GPS expires or its UTC/UART becomes invalid. Holdover remains valid when GPS disappears.
    • UTC does not require a position fix; position and velocity require a valid fix.
    • StatusTIM.GPS reports State, Baud, Time (Valid, AgeMs, AccuracyNs), Fix, Position, Velocity and Errors. Retained numeric fields must be read together with their Valid flag.
    • NMEA parsing, PPS input, flash logging/GPX, TCP bridging and Sensor60 commands are outside this feature.
    • Pure parser checks and native compilation do not establish hardware operation. Startup/configuration, actual baud, reacquisition, GPS/NTP failover and RTC seeding remain untested.

    Optional NTP Server (USE_NTP_SERVER)¶

    USE_NTP_SERVER is a separate default-off feature for personal application builds. It serves the shared clock to LAN clients on IPv4 UDP port 123 while the station is connected or the setup AP is active.

    name: lan-clock
inherit: esp32c2-2m
features:
  USE_NTP_SERVER: true
  USE_DS3231: true   # optional RTC bootstrap
  USE_NTP: false     # optional offline operation
    • Point clients at the device address of the interface they use; replies use the receiving interface and local destination address.
    • Only exact 48-byte NTPv3/v4 mode-3 requests are accepted. Replies copy the client's transmit timestamp unchanged into the originate timestamp, including a zero token.
    • At most four replies are emitted per second globally. Invalid, excess and failed requests count as drops; request/reply storage is bounded.
    • Advertised quality follows the latest accepted source: fresh GPS is stratum 1 (GPS), NTP is upstream stratum plus one, and valid manual/RTC time is an explicit local fallback at stratum 10. A never-synchronized or stale automatic source advertises unsynchronized time (LI 3, stratum 16).
    • Loss of GPS/NTP leaves the civil clock valid in holdover, but the server advertises unsynchronized time until a suitable source returns. It never silently promotes holdover to the local fallback policy.
    • There is no runtime server command, persisted server switch, DHCP advertisement, authentication, IPv6, broadcast/multicast serving, symmetric-peer mode, or extension/MAC support.
    • Selecting the feature proves no hardware timing or interoperability result; station/AP clients, concurrent refresh, source loss/recovery and malformed/flooded traffic remain untested.

    StatusTIM.NTPServer reports State (waiting, listening or failed), Quality (none, gps, ntp, local or holdover), Age in seconds, and saturating Req/Sent/Drop counters.

    Native Civil & Solar Timers (Timers / Timer1–Timer16)¶

    Normal application builds with the Time service provide 16 persistent civil timers that trigger relay outputs or Berry scripts based on clock time or solar events (sunrise/sunset):

    Timer Global & Location Commands¶

    Command Syntax Description
    Timers Timers [ON\|OFF\|TOGGLE] Queries or toggles global timer scheduling.
    Timer<n> Timer<n> [json \| 0 \| <src>] Sets, queries, clears (0), or copies from <src> (1..16) the configuration of timer <n>.
    Latitude Latitude [degrees] Sets geographic latitude (-90.000000 to +90.000000) for solar events.
    Longitude Longitude [degrees] Sets geographic longitude (-180.000000 to +180.000000) for solar events.
    Sunrise Sunrise [0..3] Sets twilight definition for solar calculations: 0 = Official (0°50'), 1 = Civil (6°), 2 = Nautical (12°), 3 = Astronomical (18°).

    Timer Configuration Fields¶

    A timer record is set using partial or complete JSON containing standard Tasmota fields:

    > Timer1 {"Enable":1,"Mode":0,"Time":"07:00","Window":0,"Days":"1111100","Repeat":1,"Output":1,"Action":1}
{"Timer1":{"Enable":1,"Mode":0,"Time":"07:00","Window":0,"Days":"1111100","Repeat":1,"Output":1,"Action":1}}
    • Enable: 1 (active) or 0 (inactive).
    • Mode:
    • 0: Clock mode (triggers at the exact local Time specified as HH:MM).
    • 1: Sunrise mode (Time is a signed offset -HH:MM or +HH:MM up to 11:59 from sunrise).
    • 2: Sunset mode (Time is a signed offset from sunset).
    • Window: Random window in minutes (0–15) to vary trigger time.
    • Days: 7-character Sunday-first weekday mask (e.g. "1111100" for Sun–Thu, "0111110" for Mon–Fri). 0 or - disables a day; any other character enables it.
    • Repeat: 1 to run indefinitely, 0 for a one-shot timer (disables itself after running).
    • Output: Target power endpoint number (1-based).
    • Action:
    • 0: Turn output OFF.
    • 1: Turn output ON.
    • 2: TOGGLE output.
    • 3: Rule / Berry Event. In Newmota, Action 3 does not blink an output; instead, it dispatches an event to the registered Berry timer handler.

    Berry Timer Callback Handler¶

    When Action 3 fires, Newmota queues an event for a script callback registered in /autoexec.be:

    def on_timer(timer_id, output, action, scheduled_epoch)
  print(string.format("Timer %d triggered for output %d at epoch %d", timer_id, output, scheduled_epoch))
end

newmota.add_timer_handler(on_timer)

    Without a registered handler, the event is quietly consumed. Rules and blink fallbacks are not implemented. Scheduling starts as soon as time is synchronized via NTP — there is no 60-second post-restart guard as in Tasmota, and missed minutes are never replayed.

    Editing timers in the browser¶

    The web UI's Configuration → Timer page lists all 16 timers with the global Timers switch and edits one at a time (mode, ± sunrise/sunset offset, random window, weekdays, repeat, output, action). It shows a warning while the device clock is unsynchronized, because timers only fire with valid time. See Web Interface.

    Ethernet and ESP32-P4 Wi-Fi¶

    Optional USE_ETHERNET adds wired Ethernet on ESP-IDF. RMII requires an ESP32, ESP32-P4 or ESP32-S31; W5500, DM9051 and KSZ8851 controllers use SPI. Configure the Ethernet pins in the device template, then use Ethernet, EthType, EthAddress and EthClockMode to configure the interface. EthIPAddress, EthGateway, EthSubnetmask and EthDNSServer1 / EthDNSServer2 configure IPv4; EthIPAddress 0.0.0.0 returns to DHCP. Changes to the PHY settings restart the device. Ethernet hardware testing is open, and Safeboot does not provide Ethernet.

    When Ethernet has an address, the setup and recovery access point stays off; it returns if the wired link drops. A Wi-Fi credential test started from the access point keeps it open until the test ends.

    The ESP32-P4 has no radio of its own. Its ESP-Hosted configuration uses an ESP32-C6 companion over SDIO. Hosted reports the companion state; HostedOta downloads and installs a companion image over plain HTTP, while HostedLoad installs one already on the filesystem. A successful update restarts the device. Hardware testing remains open.
