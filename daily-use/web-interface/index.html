    Web Interface¶

    Your device hosts its own little website: open http://<device-ip>/ (the default on Compact and Standard profiles) or https://<device-ip>/ (the default on Large profiles) in a browser, sign in with the web password you set over serial (First Steps), and you get live status, lights and relays, sensor and energy readings, GPIO and timer editors, a file editor, and interactive consoles — no cloud, no app to install.

    A normal day in the browser¶

    • Status at a glance: device identity, network address, memory, and filesystem usage refresh live (a small power snapshot every second, heavier details slower).
    • Switch things: relay cards flip your outputs, and each configured light gets its own card above them — same result as typing Power1 on or Dimmer 80 on the console. A relay that a light owns does not get a second switch.
    • Light cards: the controls follow the light's kind. A dimmer gets a brightness slider (plus a CT slider for tunable white); RGB lights get a colour wheel for hue and saturation, with a dimmer and a white or CT slider on RGBW and RGBCW lights. A mapped TuyaMCU mode also adds a white/colour button on RGBW and RGBCW lights. The wheel works from the keyboard (left/right change hue, up/down change saturation). As with Tasmota's Dimmer and Color, any nonzero brightness or a colour/CT change switches the light on, and brightness 0 switches it off while keeping the stored dimmer. Updates are sent at most every 150 ms per light, latest value wins, and are never retried.
    • Sensor and energy cards: when sensors are compiled, live temperature, humidity, pressure, and ambient light display with units and labels. Every BLE device gets its own card with RSSI, Battery, LastSeen and NMT in a footer; ages count up in the page. Each reading can show its last 24 hours as a small chart. With energy drivers, each meter instance gets its own card with a channel selector (meters are never added together).
    • Berry widgets: scripts using import widget add cards after the native ones. As in Tasmota, a script ships the card's HTML and JS; the page adds bindings, charts (lines, bars, gauges, QR codes), controls and styles, and shows the script's values only as text. At most 16 widgets, each with up to 4096 bytes of markup and 2816 bytes of data. The compact Beken page shows widgets too, with the dot-matrix and (with Matter) QR charts only. See Berry scripting.
    • Audio player: with USE_WEB_AUDIO and an I2S output in the template, Home shows the command session, source and playback state, with file or URL selection, pause, resume, stop and volume controls. Audio and codecs must be enabled in the build.
    • Matter card: with USE_MATTER, the Home page shows the Matter stack state. While a commissioning window is open it shows the fabric count, pairing code and a QR code; otherwise it offers Open commissioning window, and once a controller has joined, Remove all fabrics (with a second press to confirm). See Matter.
    • Configuration → Module and Template: edit GPIOs in Tasmota's two steps. Module picks a built-in module (or the user template, module 0) and assigns functions to the pins that template marks User. Template edits the user template itself (name, base, flag, one function per slot, User, or none), shows its JSON for copy and paste, and can activate it as Module 0. Pins that cannot support a function are not offered, reserved pins cannot be assigned, and duplicate functions block saving. Changes apply after a restart.
    • Configuration → Timer: lists all 16 Tasmota timers with the global Timers switch, and edits one timer at a time — active, mode (time of day, or sunrise/sunset with an offset up to 11:59), random window, weekdays, repeat, output, and action (off, on, toggle, Berry callback). A location card for Latitude, Longitude, and Sunrise appears when a timer uses sunrise or sunset. A warning shows while the device clock is not synchronized, because timers only fire with valid time. Unsaved edits are kept until you save or discard them.
    • Configuration → MQTT: broker settings, topics with live previews, retain options, and connection diagnostics, with explicit password keep/replace/clear. Saving a setting and the broker accepting the connection are reported separately. A Test runs a trial connection and restores the normal client afterwards.
    • Firmware Update: shows the running version and build. Update from URL saves OtaUrl and starts Upgrade 1; Upload firmware file restarts into the Safeboot recovery page (Restart 3) where the file is uploaded. See Install & Update.
    • Parallel Web & Berry Consoles: side-by-side consoles with separate input and output panes. The Web Console runs Newmota commands; the Berry Console runs Berry source in the persistent VM, up to 64 KiB. Inputs above the 2 KiB request-body size are sent in sequential chunks into a temporary heap buffer, released after compilation; source is never staged on flash. Each keeps the last 20 inputs (Up/Down); Berry preserves normal caret movement inside multiline source. Run with the button, Ctrl/Command+Enter, or Enter on a trailing blank line.
    • LittleFS File Browser and Editor: lists names, types, and sizes with per-file Edit and Delete (directories can be deleted when empty). Upload accepts several files, folder selection, and drag-and-drop; relative folder paths are kept, empty folders are not transferred. The editor handles UTF-8 text, new files, and Save As, normalizes line endings, and warns about unsaved changes. Transfers show progress and can be cancelled; an interrupted write keeps the existing file. Newmota's internal settings files are protected from browser reads and writes.
    • Onboarding Mode: when unconfigured or when the saved network fails, the device boots an open SoftAP named after its hostname, with the setup page at http://192.168.4.1 (https:// on HTTPS builds). You can scan networks and test credentials in the browser; they are committed only after association and DHCP succeed. There is no captive-portal redirect.
    • Panels that aren't ready are shown visibly disabled — the UI never shows fake values. (A Backup tab currently exists only as a mock-up.)

    Each firmware embeds one language, chosen at build time from language/ through the environment's language field (English en_GB and German de_DE ship today); there is no runtime language switch. Command names, JSON keys, and MQTT topics stay in English. If a command's answer is too large for the small device buffers, the page tells you the command may have run rather than guessing — just check with Status.

    HTTPS vs. HTTP profiles

    • Large profiles: serve HTTPS on port 443 by default, with Brotli-compressed assets and a per-device self-signed P-256 certificate generated on first start (kept at /.newmota/web-identity.bin, protected from browser access). Your browser will warn that no trusted CA issued it. A damaged identity is regenerated; if generation or TLS startup fails, the listener stays unavailable instead of falling back to HTTP.
    • Compact, Standard, and Safeboot profiles: serve HTTP on port 80 with Gzip-compressed assets.

    Switch either default in a personal build with features: {USE_WEB_HTTPS: true} (or false). An HTTP build leaves out the TLS identity generator and server. crypto: none does not affect web TLS.

    Provisioning Access (WebPassword)¶

    The listener starts after station networking is ready or the recovery SoftAP has a local address. A web password can be provisioned through the physical serial console:

    WebPassword your-device-password
    • Use 8..64 bytes. The reply is always masked ({"WebPassword":"****"}).
    • Open the device address and sign in with that password.
    • WebPassword 0 clears the credential and leaves web access open without authentication, matching standard Tasmota behavior.
    • Password changes and settings resets invalidate all active sessions.
    • Initial provisioning and password replacement are serial-only — no shared factory password or unauthenticated remote password-change route exists.

    UI and API Architecture¶

    The embedded responsive page is minified at build time — comments and layout whitespace are removed, and script and style bodies pass through rjsmin and rcssmin (they do not rename or rewrite code); pre and textarea content stays verbatim. It is then compressed (Brotli for HTTPS builds, Gzip for HTTP builds) and served verbatim; the device performs no runtime compression, so comments in index.html cost nothing on the device. The browser and the serial console share one command processor, and the page uses the same canonical STATE payload that feeds MQTT, so there is no second dashboard-only device model.

    • Fast snapshot: /api/state provides the small complete power snapshot; /api/light returns {"Lights":[…]} and accepts POST updates (endpoint plus any of power, bri, hue, sat, ct, rgb, channels).
    • Sensors: /api/sensors returns the canonical document; /api/sensors/readings returns typed values with labels and units. /api/sensors/updates returns only sensors with new data (plus more/reset/heap), and /api/sensors/updates/all marks everything first. /api/sensors/history/<series> returns one reading's last 24 hours as {"step":<seconds>,"values":[...]}. /api/energy and POST /api/energy/channel serve the meter cards.
    • Widgets: /api/widgets/updates/<since> answers what changed after a revision (every widget with its markup and data revisions, the changed data, the next revision and a per-boot generation), /api/widgets/markup/<id> returns a widget's markup, and POST /api/widgets/action takes id\nname\nvalue from a control and queues it for the script (503 when eight are waiting).
    • Bootstrap: /api/info provides authenticated read-only metadata for identity (the persisted DeviceName separate from the network hostname), network, memory, and LittleFS storage.
    • Hardware: /api/gpio/catalog and /api/gpio back the Module and Template editors; saves use the validated Module, GPIO, Template, and optional Restart 1 commands. /api/timers returns the timer switch, clock validity, location, and all 16 timers.
    • MQTT: GET/POST /api/mqtt, POST /api/mqtt/preview, GET /api/mqtt/status, and POST /api/mqtt/test.
    • Filesystem: POST /api/filesystem/list returns bounded directory pages; uploads, edits, and deletes use the transfer routes.
    • Consoles: POST /api/command submits a command; POST /api/console/command also returns the timestamped result to the sending page; POST /api/console/poll fetches bounded history; POST /api/berry/console (plus begin, chunk, run, abort for large sources) drives the Berry VM.
    • Bounds: two browser sessions; the listener's simultaneous connection count follows the platform adapter. Headers are limited to 2 KiB, command bodies to 512 bytes, and dynamic responses to 4 KiB. Berry input accepts up to 64 KiB of UTF-8 source, transferred in chunks; incomplete uploads expire after 30 seconds.
    • Session security: random session cookies, a separate CSRF token, Host/origin checks, and bounded connection counts. Commands are never retried automatically.

    Safeboot & Beken Recovery Web¶

    Network-capable Safeboot images compile a dedicated recovery HTTP service:

    • Safeboot Recovery Page: Safeboot serves a compact, authenticated recovery page from /. Newmota application users enter it using Restart 3 (or the Firmware Update page) and reconnect after reboot.
    • Bounded Browser Upload: Firmware updates are uploaded in sequential binary chunks capped at 1 KiB, verified against checksum and layout constraints before activation.
    • Safety Checks: The recovery writer targets only the application slot (app0, OTA2, or equivalent) and never touches bootloader, partition metadata, or LittleFS. Safeboot requires a configured WebPassword and fails closed without it.
    • Beken Compact Root Page: Beken has no Safeboot, so its normal application embeds one smaller English-only page with the same sidebar, responsive panels, and four themes. Home shows light cards, one switch per relay that no light owns, and energy cards; Configuration has Wi-Fi, MQTT, Module, Template, and Timers tabs; Information and the file browser show LittleFS used, free, and total; and the native RBL updater requires acknowledging that LittleFS data may be lost. It follows the normal login policy, including open access when WebPassword is empty.

    The web slice compiles on all five platform families. ESP32-S3, XH-CB3S/BK7238, BW16, and Pico 2 W have browser smoke evidence (which predates the current Beken page); BL602 has build and size evidence only, and end-to-end upload, reboot, and recovery behavior still need hardware testing.
